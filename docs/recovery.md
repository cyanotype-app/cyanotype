# Disaster recovery: rebuilding the index from the bucket

Principle ([`PLAN.md`](PLAN.md)): **S3 is the source of truth.** Postgres holds the index (what is where, plus
user-facing state). If Postgres is lost, or restored from last night's dump and so missing today's uploads,
`cyanotype reindex` reconciles the `assets` table with the bucket. It runs as a one-shot container next to the stack
(the same image as `migrate`) or from the **Reindex** GitHub workflow.

## What is stored where

| Thing | Where it lives | After a lost / stale database |
|---|---|---|
| Original photo bytes | `originals/{user}/{hash[0:2]}/{hash}.{ext}` in the bucket | untouched |
| Thumbnails, previews | `derived/{user}/{asset}/…` | untouched; regenerable |
| Which photos exist, who owns them, content hash, size, content type | **the object key and the object itself** | recovered by `reindex` |
| Original filename, upload time, client file mtime | **object user metadata** (new uploads) or **manifest** (older ones) | recovered when either exists, else `{hash}.{ext}` and the object's modification time |
| EXIF: taken time, GPS, camera, dimensions, thumbhash | inside the file | regenerated by the worker (`metadata` + `thumbnail` jobs, queued by `reindex`) |
| Search embeddings (`asset_embeddings`) | derived by the worker from `preview.webp`; in a pg_dump, never in the bucket | regenerated by the background `embed` jobs, no action needed (below) |
| RAW + JPEG pairs | derived by the worker from names and EXIF | regenerated by the metadata job; also restored from the manifest |
| Trash state, favorites, albums (title, description, cover, members) | database only; copy in the daily **manifest** | recovered from the newest manifests (see below) |
| Hidden and archived photos (`docs/library.md`, "Hidden, archive, memories and recently added") | database; one optional field each (`hidden`, `archived`) on the photo's line of the daily **manifest**, rewritten about 30 s after every hide, unhide or archive | recovered by `reindex` in the transaction that recreates the photo's row, so a restored photo is never visible first |
| Star ratings and who set them (`docs/library.md`, "Star ratings") | database; two optional fields (`rating`, `rating_source`) on the photo's line of the daily **manifest**, rewritten about 30 s after a change | recovered by `reindex` in the transaction that recreates the photo's row; a rating that came from the file is read from it again anyway |
| Tags and their photos (`docs/library.md`, "Tags") | database; one `tag` line per tag in the daily **manifest** (name, photos by hash, which were imported from the file), rewritten about 30 s after a change | recovered by `reindex`: tags the owner lacks come back with all their photos, existing tags only on photos the run recreated; only the newest manifest's tag lines count |
| Smart albums' rules (`docs/library.md`, "Smart albums") | database (`albums.rules`); the album's line in the daily **manifest** carries `rules` (no members), rewritten about 30 s after a change | recovered by `reindex` with the album and its share link; membership is never stored, so there is nothing else to restore |
| Near-duplicate groups and "Not duplicates" dismissals (`docs/library.md`, "Near-duplicates") | database only (`duplicate_*` tables): the groups are derived from the embeddings | the first check after a rebuild finds the groups again (an automatic one follows the re-embedding); **dismissals are lost**, so dismissed groups come back for review. What "Keep selected" merged (captions, place, time) is in `edits/`, the rest in the manifests |
| Users (email, role, limits, disabled flag) and the server's default limits | database; copy in the daily **account manifest** `manifests/accounts/accounts-YYYYMMDD.jsonl` | recovered by `reindex` (accounts come back with a **locked password**: `cyanotype reset-link`) |
| Passwords, sessions, API keys | database only. **Never in the bucket, on purpose** (below) | **only from the pg_dump**. After a bucket-only rebuild: new password via a reset link, sign in again, make new API keys |
| Share links (address, settings, photos of a selection) | database; copy in the per-user manifest | recovered by `reindex` into an account that has none; a password-protected link comes back **closed** until its owner sets a new password |
| Edited dates, locations and captions of photos, and their rotate / straighten / crop recipes (`docs/library.md`, "Editing a photo", "Rotate and crop") | **the bucket**: `edits/{user}/{hash[0:2]}/{hash}.json`, one small object per edited photo, written before the database changes | restored by `reindex`, as new as the last edit (not a day behind like manifests) |
| Manual "Unpair" choices, job history | database only | lost |

## What each recovery path restores

Two paths, both rehearsed by the **restore drill** (below; the table is its result on synthetic data, every row judged by
comparing the table before and after):

* **Path A**: restore the newest Postgres dump from the bucket, migrate, start the services. Use it first, whenever a dump exists.
* **Path B**: the database is lost and there is no usable dump: `cyanotype migrate`, then `cyanotype reindex --apply` from the bucket
  alone (originals, manifests, `edits/`), then a reset link per account.

| What | Path A (dump) | Path B (bucket only) |
|---|---|---|
| Original photos, thumbnails | ✅ (never in the database) | ✅ |
| Photo rows: id, owner, name, upload time | ✅ as of the dump | ✅ from the keys, object metadata and manifests (names of old photos from the manifest, else `{hash}.{ext}`) |
| Trash state, favorites | ✅ as of the dump | ✅ as of the newest manifest (up to a day old); the trash clock restarts |
| Hidden and archived photos | ✅ as of the dump | ✅ as of the newest manifest, which a hide, unhide or archive rewrites within about 30 seconds (so a photo hidden minutes before the disaster is still hidden); `reindex` reports `hidden / archived` |
| Star ratings | ✅ | ✅ as of the newest manifest (a rating change rewrites it within about 30 seconds); `reindex` reports `star ratings`; a rating read from the file comes back from the file |
| Tags | ✅ | ✅ as of the newest manifest (changes rewrite it within about 30 seconds); a restored photo's keywords are not imported again; `reindex` reports `tags / photo-tag links` |
| Smart albums | ✅ | ✅ the album, its rules and its share link as of the newest manifest (a change rewrites it within about 30 seconds); `reindex` reports `smart albums (saved rules)` |
| Near-duplicate groups | ✅ | ✅ re-found by the first check (automatic after the re-embedding) |
| Stacks: bursts | ✅ | ✅ found again by the worker |
| Stacks: made by hand, photos taken out of a burst, chosen covers (migration 0033) | ✅ | ✅ as of the newest manifest (a change rewrites it within about 30 seconds): `reindex` puts each photo back in its stack (same stack id), as taken out, or as cover, in the transaction that recreates its row, and the worker's regroup never touches these columns; `reindex` reports `stacked / unlinked / covers`. If some of a stack's photos have no original left in the bucket (or are in the trash), a stack left with fewer than two live photos is not recreated (its photos come back unstacked), and a stack whose chosen cover is gone gets another (first favorite, else earliest, among the live photos); `reindex` reports `stacks dropped / covers replaced` |
| "Not duplicates" dismissals | ✅ | ❌ not in the bucket: dismissed groups come back for review |
| The On this day, sort and stacks settings (`user_prefs`) | ✅ | ✅ as of the newest manifest (one `prefs` line per user who has changed a setting; a user with none has the defaults; a row the user already has is not overwritten); `reindex` reports `user preferences` |
| Memory dismissals (`assets.memory_dismissed`) | ✅ | ✅ as of the newest manifest (a dismissal rewrites it within about 30 seconds): put back with the photo's row; `reindex` reports `memories dismissed` |
| Trips ("Recent places", `docs/library.md`, "Trips") | n/a | n/a: derived on every request from the photos' dates and places (nothing stored, no job); after a restore they follow once the photos' places are back (the `geocode` jobs) |
| Albums and their members, covers | ✅ | ✅ as of the newest manifest |
| RAW + JPEG pairs | ✅ | ✅ (manifest, and the worker re-pairs) |
| Photo edits (date, location, caption, rotate/crop recipe) | ✅ | ✅ from `edits/`, as new as the last edit (a restored recipe is rendered again by the worker) |
| Edited JPEGs (`derived/.../edited.jpg`) and the editor's uncropped pictures | ✅ | made again on demand / by the re-render; nothing to back up (the recipe is) |
| EXIF, dimensions, thumbhash, places, bursts, search embeddings | ✅ | ✅ regenerated by the worker (embeddings last: hours for a big library) |
| Accounts: id, email, role, disabled flag | ✅ | ✅ from the account manifest, as of its newest file |
| Per-user limits, server default limits | ✅ | ✅ from the account manifest |
| Share links: address, settings, photos | ✅ | ✅ (a link revoked since the manifest was written stays revoked; see below) |
| Passwords | ✅ | ⚠️ **by design not stored**: accounts come back locked; set a new password with `cyanotype reset-link` |
| Share link passwords | ✅ | ⚠️ **by design not stored**: the link comes back closed; set a new password in the share dialog |
| API keys, sessions | ✅ (sessions of the dump) | ❌ by design: sign in again, make new keys (`cyanotype login`) |
| Invites, password reset links, admin tasks, other server state | ✅ | ❌ ephemeral: issue new invites |
| Audit log | ✅ | ❌ by design (below) |
| Usage counters (`user_usage`), upload history (`upload_log`), share view counts | ✅ | ⚠️ counters are recomputed from the restored photos; history and view counts start at zero |
| Anything changed after the dump / the newest manifest | ❌ not in the dump; recovered only where the bucket carries it (new uploads by `reindex`, edits, and new accounts' photos with `--assign-to`) | up to one day of trash/favorite/album changes and any account or share created since the newest manifest |

The drill found, on the code before this change, that path A lost nothing but path B lost every account (their photos were
skipped, or all given to whoever registered first with `--assign-to`), every limit, every album, every share link and the server
defaults. This change closes those gaps and keeps what must stay out of the bucket out.

### Decisions: what is in the bucket, and what deliberately is not

**Two-factor authentication.** Following the decision on password hashes below: *no 2FA secret and no recovery code is written to the
bucket*. A secret next to nothing it can be used with is pointless (the password hash is not there either), and a copy of the bucket
must never be a credential. So after a bucket-only rebuild (path B) every account has 2FA **off** and a locked password; the owner
signs in with a `cyanotype reset-link` password and enrols again. Path A (the Postgres dump) keeps secrets and recovery codes, but they
can only be read with the same `AUTH_TOTP_KEY`: keep it with your other secrets. The one piece of 2FA state the manifest does carry is
the admin's setting **Require 2FA** (`server_state` key `require_2fa`, the `settings` lines of the account manifest, additive: older
manifests simply lack it), so a rebuild does not silently relax the policy; it is not enforced while the server has no key.
API keys and their scopes are credentials and are not in the bucket either.

* **Passwords are not stored in the bucket.** The alternative was an owner-only manifest of argon2 hashes. Reading the bucket already
  gives every photo, so a leaked bucket key is the worst case anyway, but a hash in it would additionally let whoever copies the
  bucket (a leaked key, a bucket-listing tool, a backup of it) crack the owner's password offline, and people reuse passwords; the
  hashes in the nightly dump are the same kind of data, but there they are one object among many, and path A restores them
  anyway, so nothing is lost by keeping them out of the bucket. The cost of leaving them out is one command per account in a disaster that already
  needed a rebuild: `cyanotype reset-link --email you@example.com` prints a one-time link (the same link the admin portal makes,
  24 hours by default). Restored accounts have a locked password (an argon2 hash of a random value nobody keeps), so they cannot be
  signed in to before the owner has used the link.
* **API keys and sessions are not stored** either: they are credentials, and a key that comes back from a bucket copy is a key an
  attacker with write access to the bucket could have planted. Sign in again and make new keys.
* **Share links**: the address (token) *is* in the per-user manifest. The token is a bearer secret, but it opens only what the owner
  chose to share, and the bucket already holds all of it; without it every link ever handed out would break. A password-protected
  link keeps its address and settings but its password is not stored (same reasoning): it comes back **closed** and stays closed
  until the owner sets a new password. A link must never come back open. Links are only restored into an account that has none
  (a rebuilt database), and only from the newest manifest, so a link revoked after an older manifest, or after the dump, is not
  resurrected. The window that remains: a link revoked after the newest manifest was written, in a rebuild, comes back; revoke it again.
* **The audit log is not stored** in the bucket. It records who did what, can grow without bound, is operational rather than library
  data, and path A restores it. Path B starts a new log.
* **Account deletion** removes the account from the next account manifest; reindex only reads the newest file, so a deleted account
  is not recreated from an older one.

## The restore drill

`scripts/restore-drill.sh` (`just restore-drill`) rehearses both paths on a throwaway stack and prints the table above for the
checkout it runs on; `docs/restore-drill-report.md` is the committed result (synthetic data only). It:

1. builds the real images and starts a separate compose project, `cyano-drill` (`infra/drill/docker-compose.yml`; Postgres on
   127.0.0.1:54397, the bucket on :18397, the gateway on :3397, its own volumes; never the default project);
2. seeds a library through the real APIs: an admin, a member (by invite), photos with EXIF (test photos from the repo's fixtures and a
   CC0 RAW sample cached under `models/eval/raw`, or `DRILL_RAW_CACHE`), a burst, a RAW + JPEG pair, albums, share links, favorites, a
   trashed photo, edits, an invite, limits and API keys, and waits for the worker (thumbnails, EXIF, geocode, embeddings, bursts);
3. writes the manifests, runs the real backup job, takes the canonical snapshot (per-table row hashes plus API responses: timeline,
   albums, a fixed search, photo details with edits, the share page);
4. path A: drops the database volume, restores the dump as `deploy.md` says, migrates, starts, snapshots; path B: drops it again,
   migrates, `reindex --apply`, reset links, worker catch-up, snapshots;
5. diffs both against the first snapshot and writes the report (stdout and `--report FILE`), then tears everything down unless `--keep`.

It needs docker compose, python3 and curl, 5 GB of free disk and about 25 minutes the first time (the image build; a few minutes after).
A manual GitHub workflow (**Restore drill**, `workflow_dispatch`) runs the same script; it is not a required check.

### How long recovery takes (measured small, extrapolated)

The drill's library is 18 tiny files, so its timings are mostly fixed costs; `docs/restore-drill-report.md` has the measured
steps. Extrapolation to **about 2,000 photos and 25 GB** (an estimate, not a measurement; the drill has not been run at that size):

| Step | Drill (18 files) | 2,000 photos, 25 GB | What scales |
|---|---|---|---|
| Path A: download and restore the dump, migrate, start | about 15 s | **1 to 3 minutes** | the dump (tens of MB at this size: rows plus 2,000 search vectors), not the photos |
| Path B: `reindex` (listing, one HEAD per photo, manifests, edits) | about 4 s | **under 1 to 2 minutes** | photo count (16 HEADs in parallel); not bytes |
| Path B: reset links, sign in again | about 7 s | **a few minutes of your time** | accounts |
| Path B: the worker catches up (EXIF, thumbnails, previews, places, bursts) | about 15 s | **roughly 30 to 60 minutes** | photo count and bytes: every original is read once (25 GB) and decoded; about 0.5 to 1.5 s of CPU per 12-megapixel photo |
| Path B: search embeddings (last, in the background) | within the 15 s above | **about 20 to 30 minutes** (`docs/build.md`: 8 hours per 50,000 photos at the default one thread) | photo count |

The library is browsable as soon as `reindex --apply` has finished and the stack is up (rows exist; thumbnails that are still in the
bucket under the old asset ids are shown at once); path B is fully "done" (search included) in roughly one to one and a half hours.
Path A is done in minutes, which is the reason to keep the dumps.

### Real-data drill (`--source real`, read-only)

Built to answer "would my real backup and my real bucket recover?" **without touching either.** It restores the newest real
dump into a local throwaway Postgres, then runs `reindex` against the real bucket twice with a read-only key: a dry run against the
restored dump (what the dump is missing), and an apply into a *second* local database (path B, bucket only), and compares the two
databases with the same snapshot. It never starts the services or the worker, never contacts your live server, and writes nothing to
the bucket.

Safety, enforced by the script: it refuses to run unless a test PUT of a tiny object under `drill-probe/` with your key is **denied**
(if the write succeeds it deletes what it wrote and stops with exit status 3; on a versioned bucket a delete marker stays, remove it by
hand); it aborts with less than 10 GB free; only the dump (small) and listings are downloaded: `reindex` lists keys, HEADs objects and
reads only the small manifest and `edits/` objects, never an original, and its container has a read-only filesystem and a 16 MB tmpfs.
The report holds counts and verdicts only (no names or emails) but describes your library: do not commit it. The first real run
shows path B without accounts until a release with the account manifest has run once (`cyanotype manifest`, or wait for the daily job).

**Create the read-only key** (Linode Object Storage, Cloud Manager): *Object Storage, Access Keys, Create an Access Key*; name it
`cyanotype-drill-ro`; turn on **Limited Access**; for your bucket choose **Read Only** (leave every other bucket at None); create it and
copy the secret once (it is not shown again). With `linode-cli` the same is
`linode-cli object-storage keys-create --label cyanotype-drill-ro --bucket_access '[{"region":"<region>","bucket_name":"<bucket>","permissions":"read_only"}]'`.
Delete the key when the drill is done. Then, from a checkout (not on the server):

```sh
export DRILL_S3_ENDPOINT=https://<region>.linodeobjects.com   # your bucket's endpoint
export DRILL_S3_BUCKET=<bucket>
export DRILL_S3_ACCESS_KEY_ID=<read-only access key>
export DRILL_S3_SECRET_ACCESS_KEY=<read-only secret key>
# optional: DRILL_S3_REGION (default us-east-1), DRILL_S3_BACKUP_PREFIX (default backups/postgres)
scripts/restore-drill.sh --source real --report ~/cyanotype-real-drill.md
```

### Self-describing originals (object metadata)

Since this feature shipped, every new upload (direct presigned multipart and the proxied browser path alike; both
start with `CreateMultipartUpload`, so clients send nothing extra) stores S3 user metadata on the original:

| Header | Content |
|---|---|
| `Content-Type` | the content type the client reported (as before) |
| `x-amz-meta-cyanotype-name` | original filename, percent-encoded (S3 metadata is ASCII; very long names are clipped on a character boundary, keeping the extension) |
| `x-amz-meta-cyanotype-owner` | owner user id |
| `x-amz-meta-cyanotype-created` | upload time (RFC 3339) |
| `x-amz-meta-cyanotype-mtime` | client-reported file mtime, when the importer sent one |
| `x-amz-meta-cyanotype-v` | layout version (`1`) |

Uploads that were already in flight when this shipped (and every object uploaded earlier) simply have no such
metadata; nothing breaks, `reindex` falls back as the table above says.

### Manifests (state the bucket cannot carry)

Object metadata is written once at upload and can never say "this photo is now in the trash / a favorite / in album
X", and old objects have none. So the assets service also writes, once a day and per user,
`manifests/{user}/originals-YYYYMMDD.jsonl` (the first pass runs 15 minutes after start-up): one JSON object per
line, a `meta` header, every `asset` (id, hash, key, name, content type, size, created/mtime/taken times, trash
time, favorite flag when the schema has one, the `hidden` and `archived` flags (optional; absent in manifests from before they existed, which read as neither), the hash of its JPEG if it is a stacked RAW, and, only where set, the owner's stack decisions: `stack` (the id shared by the members of a stack made by hand), `stack_unlinked` and `stack_cover`, and `memory_dismissed`) and every `album` (id,
title, description, cover and members by hash) and every share link (`share`: id, token, kind, album or photos by hash,
title, settings; **never a password**), every tag and, when the user has changed one, a `prefs` line (the On this day, sort and stacks switches). Next to them, one account manifest for the whole server,
`manifests/accounts/accounts-YYYYMMDD.jsonl`: every account (id, email, role, created, disabled, the three limits) and the
server's default limits; **never a password hash, API key or session** (it is not written while the users table is empty, so
a freshly created database cannot push the real accounts out). Manifest format 2 adds the `share` lines; a version 1 manifest
(no shares) and the older `reindex` reading a version 2 one (it counts the lines it does not know) both keep working. Format 4 adds the `prefs` line and the stack fields; the same holds both ways: a manifest without them restores with no stacks and default switches, and an older `reindex` ignores the fields and counts the `prefs` line as one it does not know. `memory_dismissed` is another optional field of format 4 rather than a format 5: `reindex` does not branch on the format version for it (only for tags), a manifest without it reads as nothing dismissed, and an older `reindex` ignores it.
`MANIFEST_KEEP` (default 14, `0` turns it off) is how many daily
files are kept. `cyanotype manifest` writes today's immediately.

**Why dated files:** if the database is restored from an old dump and the assets service then writes a manifest
from that stale data, only that day's file is replaced; the earlier ones survive. `reindex` merges all of a user's
manifests, newest first, the first entry for a photo winning; accounts and share links come only from the **newest** file (so a
deleted account or a revoked link is not brought back by an older one).

**Why both metadata and manifests** (the trade-off): metadata makes each object independently recoverable with
zero extra moving parts, but it is immutable, and writing it onto old objects needs a self-copy (below). The
manifest is cheap, covers old objects and mutable state, but is only as fresh as its last run (up to a day behind)
and is derived data that can itself be stale. Neither alone is enough; together they cover everything that can be
covered.

### Backfilling metadata onto existing originals (optional, think first)

`reindex --backfill-metadata --apply` writes the metadata onto originals that have a row but no metadata, with a
`CopyObject` of the object onto itself (`MetadataDirective=REPLACE`). **The bucket is versioned: a self-copy creates
a new version holding a full copy of the bytes. Until the old version is expired or purged, each backfilled object
costs double storage** (a 50 GB library briefly becomes 100 GB billed, and it counts against the bucket's
lifecycle rules, not against `TRASH_RETENTION_DAYS`). It is off by default and is not needed if the daily manifests
exist: the manifest already carries the names of old photos. Use it only if you want the bucket to be recoverable
without manifests, and only after you have a lifecycle rule that expires noncurrent versions. Objects over 5 GiB
cannot be copied this way and are reported. Reindex never deletes the old versions itself.

## Finding damage before you need this: the nightly integrity check

Recovery is only as good as the bucket, so the worker looks at the bucket every night (`docs/admin.md`, "Storage integrity"):
originals the database lists but the bucket lost, objects no row points at, and originals whose bytes no longer match their sha256
(a rolling sample, oldest-verified first). Admin > Health lists the findings. The fixes reuse what this document describes:
**Restore from a previous version** makes an earlier version of the object current again (the versioned bucket keeps them until the
photo is purged; the version chosen is the one whose hash is the stored one), and **Restore as photo** is `reindex --apply` for a single
object (the row, the jobs and the `edits/` object; albums, pairs, tags and share links come only from a whole-library `reindex`).
Purging a photo deletes its versions on purpose, so nothing here fights it: a photo in the trash or being purged is never reported,
and the check never deletes anything by itself.

## The `reindex` command

```sh
docker compose run --rm reindex [flags]          # dev; in production: dc run --rm reindex [flags]
```

| Flag | Meaning |
|---|---|
| *(none)* / `--dry-run` | **Default.** Report only; writes nothing anywhere. |
| `--apply` | Write. Needed for everything below to take effect. |
| `--assign-to EMAIL` | Objects whose owner id has no `users` row are normally skipped and reported; with this they go to that existing account (register it first). Their keys keep the old owner in the path; that is fine. Albums and trash state are not restored for them. |
| `--mark-missing` | Move rows whose original object is gone to the trash (a RAW stacked behind such a primary goes with it; a missing RAW is detached first so its JPEG stays). Rows are never deleted. |
| `--rethumb` | Re-queue the thumbnail job for rows whose `derived/…/thumb.webp` or `preview.webp` is gone (and that have no thumbnail job waiting). |
| `--backfill-metadata` | See above. Needs `--apply`. |
| `--no-manifest` | Ignore `manifests/`. |
| `--concurrency N` | Parallel S3 HEAD requests (default 16). |
| `--min-age-secs N` | Skip objects modified within the last N seconds (default 600; an upload may be registering). |
| `--json` | Print the report as one JSON line at the end (the last line of stdout) instead of text. |

What it does, in order:

1. Lists `derived/` (to learn which thumbnails exist).
2. Lists `originals/` page by page (1000 keys; current versions only, so a key whose newest version is a delete
   marker is not an object). For each object it parses the key (anything not shaped like
   `originals/{uuid}/{xx}/{sha256}.{ext}` is counted, listed as an example and **never touched**) and looks the page
   up in Postgres by `(owner, sha256)`.
   * **Row exists:** counted. A row in the trash is left alone. A row queued for permanent deletion
     (`purging_at`) is left alone and **its object is not resurrected**, and never backfilled.
   * **Same content already indexed under another key** (e.g. another extension): counted as an extra copy; no row.
   * **No row (orphan):** with `--apply`, one row per object, in one transaction with its `metadata` and `thumbnail`
     jobs (enqueue is idempotent): owner from the key, hash from the key, `original_name` from the object
     metadata, else the manifest, else `{hash}.{ext}`, content type and size from the object, `created_at` from
     the metadata, else the manifest, else the object's modification time. If a manifest knows the photo, the row
     gets its **original asset id** back (so thumbnails already in the bucket still belong to it), its trash state
     (the trash clock restarts: it is deleted `TRASH_RETENTION_DAYS` after the reindex, not from the old time) and
     its favorite flag. An owner that does not exist is skipped (counted per user) unless `--assign-to`.
3. Walks the `assets` table in id order. Rows (not purging) whose key the listing did not show are confirmed with a
   HEAD before being called **missing**; with `--mark-missing` live ones go to the trash. Rows whose thumbnail or
   preview is missing are counted; with `--rethumb` their job is re-queued. A pending job (queued or running)
   means "being made", not "missing".
4. **Edits** (after the orphans were recreated): every object under `edits/` is applied to the photo with that owner and content
   hash when the row has no edits or older ones (`edited_at` is compared with the object's `updated_at`). This is the one place
   `reindex` rewrites a row that already exists, on purpose: an edit is what the user asked for, the object is written before the
   database, and so a database restored from a dump older than an edit gets it back. A photo whose edits were all reverted keeps an
   empty object, which puts a restored dump's older edit back to the file's values. Re-queues the geocode job (a new location) and
   the burst regrouping (a new time) like the edit itself. Objects of a user that no longer exist go to `--assign-to`; objects that
   are not valid are counted and left alone. In a dry run an edit of a photo that is still an orphan counts as "no photo yet".
5. With manifests: albums that no longer exist are recreated with their members and cover; for albums that exist,
   only the photos recreated in this run are added (an album you changed after the dump is never rewritten);
   recreated RAWs are re-stacked behind their JPEGs.

It is **idempotent and resumable**: it keeps no state, every write is `ON CONFLICT DO NOTHING` or an idempotent
enqueue, so a killed run is simply run again. It streams page by page; memory is a set of 64-bit hashes of the keys
seen (a few MB for tens of thousands of objects). Progress is logged as JSON lines like every service. Exit status
is non-zero when any request or write failed (`errors` in the report): run it again.

It **never deletes or overwrites anything in the bucket**. Its only bucket write is `--backfill-metadata`.
Derived objects of photos whose rows are gone and whose ids were not in a manifest are left behind as unreferenced
files under `derived/` (harmless; the new row gets fresh thumbnails under its new id).

## Runbook: Postgres lost, or restored from a dump that is behind

Do this on the server (`dc` is the compose shorthand from [`deploy.md`](deploy.md)), or use the workflow for steps 4
and 6.

1. **Stop the writers** so nothing races the recovery and the stale database never writes a manifest:
   `dc stop auth assets worker`.
2. **Restore the newest dump** (see "Restore" in [`deploy.md`](deploy.md)): `dc run --rm backup list`, then
   `dc run --rm -e CONFIRM=yes backup restore` (newest by default), then `dc run --rm migrate`.
   If there is **no dump at all** (path B): `dc run --rm migrate` gives an empty schema. **Do not register an account**: reindex
   recreates every account from `manifests/accounts/` in the bucket (same ids, emails, roles, limits), which is what gives the
   photos their owners. (If you registered one anyway, or the bucket has no account manifest yet because the release that writes it
   never ran, the old way still works: register, then use `--assign-to you@example.com` in steps 3 and 6; every photo goes to
   that account and albums, trash and limits of other accounts are not restored for them.)
3. **Dry run** (writes nothing): `dc run --rm reindex` (workflow: mode `dry-run`). Read the summary:
   * `orphans` is what the dump was missing; `would be recreated` should match it.
   * `accounts in manifest / to restore / have` should list your accounts (path B: all to restore); `email taken by another account`
     must be 0.
   * `skipped, owner does not exist` must be 0, or you meant `--assign-to`.
   * `keys not shaped like originals` should be 0.
   * `rows whose original is missing` should be 0; if not, find out why before using `--mark-missing`.
4. **Review**: spot-check the examples. If `manifests: users` is 0 although you expect manifests, check
   `manifests/` in the bucket before applying (without them names of old photos fall back to the hash).
5. If the dry run is surprising, stop here: nothing has been written.
6. **Apply**: `dc run --rm reindex --apply` (add `--rethumb`, and `--mark-missing` if you reviewed those rows).
   Workflow: mode `apply`, confirm `REINDEX`. Re-run any time; the second run should report zero orphans.
7. **Bring the stack up**: `dc up -d --wait`. The worker drains the queued `metadata` and `thumbnail` jobs: EXIF,
   dimensions, thumbnails and RAW/JPEG pairing come back over the next minutes to hours (about the speed of a fresh
   upload).
   Search comes back last: the worker's embedding sweep (at start, then every 15 minutes) queues every photo that has a
   preview but no vector, behind all thumbnails, and a library of 50,000 photos takes about 8 hours at the default
   one thread (SigLIP 2; 2 hours with CLIP) (`docs/build.md`, "Memory, speed and sizes"). Until then search says "Still indexing N photos"; filters work at once. A
   restored dump that already contains the vectors needs none of this.
   **Path B only, right after the stack is up: give each owner a way in.** The restored accounts have locked passwords. For each
   account (the admin first): `dc run --rm --entrypoint /usr/local/bin/app reindex reset-link --email you@example.com` (the
   `reindex` service is just the CLI image with the database and bucket variables). It prints `/reset-password?token=...`; put your site's address in
   front of it, open it in a browser and choose a password (the link works once, for 24 hours). The admin can then make links for
   the other accounts in the admin portal, and each person makes a new API key (`cyanotype login`). Re-set the password of any
   password-protected share link in its share dialog.
8. **Verify**: log in, check the photo count (`cyanotype status`), open the trash, an album, a recent upload. Run
   `dc run --rm reindex` once more: everything should be "already indexed", 0 orphans, 0 errors.

Server lost completely: new VPS, `.env.prod` and bucket as before, deploy steps 1 to 8, `dc up -d postgres`, then the
runbook from step 2.

### What you can and cannot get back

* **Back, exactly:** every original and its owner, hash, size, content type; thumbnails (regenerated); EXIF and
  everything the worker computes.
* **Back, from the bucket:** edited dates, locations and captions, as of the last edit.
* **Back, if a manifest or metadata exists:** original filenames, upload times, file mtimes, trash state (clock
  restarted), favorites, albums, RAW/JPEG pairs, original asset ids. State is as of the newest manifest (up to a day
  old, or older if manifests had stopped).
* **Back, from the account manifest:** accounts (id, email, role, limits, disabled flag), the server's default limits and share
  links (password-protected ones closed). Passwords come back only by a reset link (above).
* **Back from the dump only:** passwords, sessions, API keys, invites, the audit log, and anything changed since the dump when no
  manifest covers it. With a dump but no manifests, photos uploaded after the dump come back with hash names and
  without albums, trash or favorites.
* **Never back:** manual "Unpair" decisions, job history, photos whose original object was permanently deleted
  (purged photos are gone by design; a restored dump may still list them: use `--mark-missing`).
* **Changes after the dump to rows that already exist** (renames, trashing, favorites, album edits) are not
  re-applied: existing rows are never rewritten. This is deliberate; the dump is the authority for rows it has.
